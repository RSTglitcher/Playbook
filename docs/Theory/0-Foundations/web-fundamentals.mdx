### 🌐 HTTP Protocols & Communication Styles

:::tip

**Definition**
The foundation of data exchange on the web, bridging client requests to server resources across stateless transport channels.
:::

> **Interview Pitch:** *"HTTP is a stateless protocol where state is maintained at the application layer, trading connection overhead across protocol generations (HTTP/1.1 to HTTP/3) to optimize transport latency."*

#### 🧠 Decision Drivers
* **Choose REST (HTTP/JSON):** Standard CRUD APIs, external public integrations, resource-oriented modeling.
* **Choose GraphQL:** Complex graph relationships, mobile clients requiring precise field filtering (preventing over-fetching).
* **Choose WebSockets:** Low-latency bi-directional streaming (chat apps, live financial dashboards, collaborative tools).

#### 🧬 Core Primitives & Off-the-Cuff Explanations

| Mechanism | Off-the-Cuff Explanation | Architectural Impact / Mechanism | Deep-Dive Research Term |
| :--- | :--- | :--- | :--- |
| **HTTP/1.1 vs HTTP/2** | HTTP/1.1 uses text sequential requests; HTTP/2 multiplexes binary streams over a single TCP connection. | HTTP/2 eliminates browser connection limits and head-of-line blocking at the application layer. | Multiplexing, Binary Framing, HPACK |
| **Idempotency** | Safe operations (GET, PUT, DELETE) produce the same result regardless of execution count; unsafe (POST) mutates repeatedly. | Enables safe retry logic in distributed API gateways without accidental duplicate records. | HTTP Methods, Retry Safety |
| **Content Negotiation** | Headers (`Accept`, `Content-Type`) negotiating format and encoding between client and server. | Controls payload formatting (JSON vs. Protobuf) and compression streams (`gzip`, `br`). | REST Media Types, Accept Headers |

#### 🚨 Misapplication Diagnostics in Production

| Concept | Misapplication Scenario | Production BAU Symptom / Telemetry | Remediation |
| :--- | :--- | :--- | :--- |
| **Non-Idempotent Retries** | Retrying failed HTTP `POST` requests automatically at the gateway level during network drops. | Duplicate database record creation (e.g., charging a credit card twice). | Implement **Idempotency Keys** (`X-Idempotency-Key`) in API request headers. |
| **Chatty APIs** | Forcing mobile apps to make 20+ sequential HTTP/1.1 GET requests to construct a single screen. | Severe network latency spikes, mobile battery drain, and request queuing delays. | Use GraphQL or aggregate BFF (Backend-For-Frontend) endpoints to batch data. |

### 🔑 State Management, Sessions & Auth

:::tip

**Definition**
Techniques for maintaining continuity, identity, and user context across stateless HTTP request cycles.
:::

> **Interview Pitch:** *"State management balances server-side session memory against stateless JWT self-containment—trading instant session revocation for effortless horizontal scaling."*

#### 🧠 Decision Drivers
* **Choose Server-Side Sessions (Redis):** High security requirements, immediate session revocation needs (e.g., banking apps, admin portals).
* **Choose Stateless JWT Tokens:** High-scale microservices, cross-domain SSO, edge-authenticated APIs.

#### 🧬 Core Primitives & Off-the-Cuff Explanations

| Mechanism | Off-the-Cuff Explanation | Architectural Impact / Mechanism | Deep-Dive Research Term |
| :--- | :--- | :--- | :--- |
| **Server-Side Session** | Client stores a `Session ID` cookie; server looks up state in centralized memory store (Redis). | Secure and easy to revoke instantly; requires distributed cache lookups on every request. | Session Hydration, Sticky Sessions |
| **JWT (Stateless Token)** | Self-contained, digitally signed JSON payload sent in authorization headers. | Zero database lookups to verify identity; impossible to revoke before expiration without a blacklist. | Cryptographic Signatures, Claims |
| **HTTP Cookies** | Key-value client storage automatically attached to outgoing HTTP requests by the browser. | Subject to CSRF attacks unless strictly guarded with browser isolation flags. | `HttpOnly`, `SameSite`, `Secure` |

#### 🚨 Misapplication Diagnostics in Production

| Concept | Misapplication Scenario | Production BAU Symptom / Telemetry | Remediation |
| :--- | :--- | :--- | :--- |
| **Bloated JWTs** | Storing large user permission lists and context objects directly inside the JWT payload. | Unnecessary network bandwidth consumption on every request; header size limit errors (413/431). | Keep JWT payloads minimal (User ID + Roles); fetch granular permissions from cache. |
| **Local In-Memory Sessions** | Storing session state directly in single application server node memory without Redis. | Users constantly logged out whenever traffic routes to a different server instance (unless using sticky sessions). | Move session state to an external shared cache (Redis) or switch to JWT tokens. |

  </TabItem>

### 🖥️ Rendering Models & Architecture

:::tip

**Definition**
Strategies determining where UI template parsing, data fetching, and HTML rendering take place along the client-to-server path.
:::

> **Interview Pitch:** *"Rendering models trade server compute for client performance—balancing fast initial page loads and SEO (SSR) against rich interactive user experiences (CSR)."*

#### 🧠 Decision Drivers
* **Choose SSR (Server-Side Rendering):** SEO-driven sites, dynamic landing pages, content portals, fast initial load priorities.
* **Choose CSR (Client-Side Rendering):** Gated dashboards, highly interactive SaaS applications, offline-first PWAs.
* **Choose Static (SSG / ISR):** Documentation sites, blogs, stable e-commerce catalog pages.

#### 🧬 Core Primitives & Off-the-Cuff Explanations

| Model | Off-the-Cuff Explanation | Architectural Impact / Mechanism | Deep-Dive Research Term |
| :--- | :--- | :--- | :--- |
| **SSR** | Server executes template logic and returns fully rendered HTML to the browser. | Fast Time-To-First-Byte (TTFB) and SEO; increases server CPU load under high traffic. | Server Hydration, Edge Rendering |
| **CSR** | Server returns empty HTML shell + JS bundle; browser executes JS to render UI. | Rich client interactivity; slower initial load speed and SEO rendering challenges. | Virtual DOM, Client Hydration |
| **MVC Architecture** | Separates application data (Model), UI (View), and routing/logic (Controller). | Clean separation of concerns; prevents business logic from polluting rendering templates. | Separation of Concerns |

#### 🚨 Misapplication Diagnostics in Production

| Concept | Misapplication Scenario | Production BAU Symptom / Telemetry | Remediation |
| :--- | :--- | :--- | :--- |
| **Pure CSR for SEO** | Building public marketing or e-commerce catalog sites as single-page CSR React apps without SSR. | Poor search engine indexing, low search rankings, and blank-screen delays on slow mobile networks. | Adopt SSR or Static Site Generation (SSG) with frameworks like Next.js or Astro. |
| **SSR Server Bottlenecks** | Executing un-cached heavy database queries during SSR HTML generation on every request. | High server CPU load, degraded TTFB latency, and server crashes during traffic spikes. | Cache database queries at the edge or implement Incremental Static Regeneration (ISR). |

  </TabItem>

### 🔒 Security & Browser Isolation Boundaries

:::tip

**Definition**
Browser-enforced policies and HTTP headers designed to sandbox client web applications and protect resources from unauthorized cross-domain access.
:::

> **Interview Pitch:** *"Browser security enforces origin isolation—using SOP and CORS to prevent rogue domains from making unauthorized requests or reading cross-origin data."*

#### 🧠 Decision Drivers
* **Enforce CORS:** When exposing public or multi-domain APIs to third-party frontends.
* **Enforce Strict Cookies:** When storing authentication tokens in browsers to prevent XSS and CSRF token theft.

#### 🧬 Core Primitives & Off-the-Cuff Explanations

| Mechanism | Off-the-Cuff Explanation | Architectural Impact / Mechanism | Deep-Dive Research Term |
| :--- | :--- | :--- | :--- |
| **Same-Origin Policy (SOP)** | Core browser security rule preventing scripts on domain A from reading data on domain B. | Protects user session privacy across different domains by default. | Origin (Scheme + Host + Port) |
| **CORS** | Server-driven mechanism relaxing SOP to allow specific cross-origin domains. | Prevents browser clients from blocking legitimate API calls across microservice domains. | Preflight (`OPTIONS`), Access-Control Headers |
| **Cookie Isolation Flags** | Security directives (`HttpOnly`, `SameSite=Strict`, `Secure`) attached to cookies. | `HttpOnly` blocks JS access (prevents XSS theft); `SameSite` blocks cross-domain attachment (prevents CSRF). | XSS, CSRF Mitigation |

#### 🚨 Misapplication Diagnostics in Production

| Concept | Misapplication Scenario | Production BAU Symptom / Telemetry | Remediation |
| :--- | :--- | :--- | :--- |
| **Wildcard CORS (`*`)** | Setting `Access-Control-Allow-Origin: *` while enabling `Access-Control-Allow-Credentials: true`. | Severe security vulnerability; malicious websites can read authenticated user data. | Specify explicit allowed origins dynamically based on whitelist configurations. |
| **Storing Tokens in LocalStorage** | Saving JWT auth tokens in browser `localStorage` or un-flagged cookies. | Complete account takeover via XSS attacks (malicious injected JS script reads token). | Store tokens in **`HttpOnly` + `SameSite=Strict` + `Secure` cookies**. |

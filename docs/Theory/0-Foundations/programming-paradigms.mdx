## 🧠 Theory
Functional Programming provides a set of **conceptual tools** for modelling software as transformations of data through pure, predictable functions.
Where OOP models *objects and behaviour*, FP models *data and transformations*.

FP constructs help analysts and engineers:

- reason about systems without hidden state
- avoid side‑effect‑driven bugs
- design predictable, testable flows
- scale concurrency safely
- simplify complex transformations

---

:::tip Definition
A set of conceptual building blocks for modelling software using **pure functions**, **immutable data**, and **predictable transformations**.
:::

**When to Use**

- When correctness and predictability matter
- When concurrency or parallelism is required
- When transformations dominate behaviour
- When avoiding shared mutable state is beneficial

**When Not to Use**

- Highly stateful, object‑rich domains
- Systems requiring heavy mutation or lifecycle modelling
- Environments where recursion or immutability is costly

---

## 🎯 What Problem Does This Solve?

FP constructs solve the problem of **unpredictability caused by mutable state and side effects**.
They provide a vocabulary for:

- expressing logic as pure transformations
- eliminating hidden dependencies
- enabling safe concurrency
- simplifying reasoning about system behaviour
- reducing accidental complexity

They help Technical Analysts reason about **data flow**, **state transitions**, and **deterministic behaviour**.

---

## 🧠 Conceptual Model

### **Core Components**

- **Pure Functions** — same input → same output, no side effects
- **Immutability** — data cannot be changed, only transformed
- **Higher‑Order Functions** — functions that take or return functions
- **Function Composition** — building pipelines of transformations
- **Recursion** — looping via self‑reference
- **Side Effects** — interactions with the outside world
- **Monads** — structured handling of effects
- **Referential Transparency** — expressions can be replaced with their values

### **Axes of Variation**

- Strict vs lazy evaluation
- Pure vs impure languages
- Immutable‑first vs mutable‑allowed
- Recursion vs iteration
- Expression‑oriented vs statement‑oriented

---

### **Typical Lifecycle or Flow**

```
[Input Data]
      ↓
[Pure Function]
      ↓
[Transformed Data]
      ↓
[Composed with Other Functions]
      ↓
[Final Output]
```

## 📘 Key Terminology

| **Term** | **Definition** | **Languages** |
| --- | --- | --- |
| **Pure Function** | A function with no side effects; same input → same output. | Haskell, Scala, F#, Elm, OCaml, JavaScript (FP style), Python (FP style) |
| **Immutability** | Data cannot be changed after creation; new values are produced instead. | Haskell, Scala, Clojure, Elm, F#, Rust (by default), Java/Kotlin (optional) |
| **Higher‑Order Function** | A function that takes other functions as arguments or returns them. | All FP languages; also JavaScript, Python, Java (lambdas), C# |
| **Function Composition** | Combining functions so the output of one becomes the input of another. | Haskell, Scala, F#, Elm, JavaScript (FP style), Python (FP style) |
| **Referential Transparency** | An expression can be replaced with its value without changing program behaviour. | Haskell, Elm, FP‑first Scala, F# |
| **Side Effect** | Any interaction with the outside world (I/O, mutation, logging) that breaks purity. | All languages (conceptual) |
| **Monad** | A structure for sequencing computations with controlled effects. | Haskell, Scala (Cats/ZIO), F#, Elm |
| **Functor** | A structure that can be mapped over (supports ``map``). | Haskell, Scala, F#, Elm |
| **Applicative** | A structure that applies wrapped functions to wrapped values. | Haskell, Scala (Cats/ZIO), F# |
| **Algebraic Data Type (ADT)** | A type formed by combining other types (sum + product types). | Haskell, Scala, Rust, Elm, F# |
| **Pattern Matching** | A mechanism for destructuring and branching on ADTs. | Scala, Haskell, Rust, F#, OCaml, Elm |
| **Recursion** | A function that calls itself to process data. | All FP languages; also Python, JS, Java |
| **Lazy Evaluation** | Expressions are evaluated only when needed. | Haskell (default), Scala (optional), Clojure (optional) |
| **Currying** | Transforming a function of multiple arguments into a chain of single‑argument functions. | Haskell, Scala, F#, Elm, JavaScript (FP style) |

---


## 🧠 Theory
Object‑Oriented Programming (OOP) provides a set of **conceptual tools** for modelling real‑world systems using objects, relationships, and behaviours.
Where **Workbench** languages implement these constructs, **Theory** explains *why they exist*, *what problems they solve*, and *how they behave under pressure*.

OOP constructs help analysts and engineers:

- structure systems around meaningful boundaries
- reduce accidental complexity
- model behaviour and state
- manage change safely
- reason about interactions between components

---

:::tip Definition
A set of conceptual building blocks for modelling software using **objects**, **relationships**, and **behaviours**.
:::

**When to Use**

- When modelling domains with clear entities and behaviours
- When you need predictable structure and encapsulation
- When designing systems that evolve over time

**When Not to Use**

- Highly functional or data‑flow‑oriented systems
- Purely stateless transformations
- Situations where inheritance introduces more complexity than value

---

## 🎯 What Problem Does This Solve?

OOP constructs solve the problem of **managing complexity** in large, evolving systems.
They provide a vocabulary for:

- grouping related data and behaviour
- hiding internal details
- defining clear contracts
- modelling variation and extension
- controlling how components interact

They help Technical Analysts reason about **system boundaries**, **responsibilities**, and **change over time**.

---

## 🧠 Conceptual Model

### **Core Components**

- **Encapsulation** — bundling data + behaviour, hiding internal details
- **Inheritance** — reusing and extending behaviour
- **Polymorphism** — treating different types through a common interface
- **Abstraction** — exposing only essential behaviour
- **Composition** — building complex behaviour by combining objects
- **Interfaces** — defining contracts without implementation
- **Classes vs Instances** — blueprint vs concrete object
- **Object Lifecycle** — creation → usage → destruction
- **SOLID Principles** — guidelines for maintainable OOP design

### **Axes of Variation**

- Static vs dynamic typing
- Single vs multiple inheritance
- Interface‑based vs class‑based polymorphism
- Composition‑first vs inheritance‑first design
- Mutable vs immutable objects

---

### **Typical Lifecycle or Flow**

```
[Class Defined]
      ↓
[Instance Created]
      ↓
[State Mutated / Methods Called]
      ↓
[Interactions with Other Objects]
      ↓
[Object Becomes Unreachable]
      ↓
[GC / Destruction]
```

---

:::info How a TA Evaluates This Concept
- Does the abstraction reduce or increase complexity?

- Is inheritance being used safely, or should composition replace it?

:::

**What happens when:**

- **Data grows** → object graphs deepen; memory pressure increases
- **Traffic increases** → polymorphic dispatch cost becomes visible
- **Concurrency rises** → shared mutable state becomes a bottleneck
- **Resources become constrained** → object lifecycle management matters

## "Language Theory"
---

:::tip
### Definition
A **programming language** is a formal system of syntax and semantics that allows humans to express computations in a way that machines can execute.
:::

**When to Use**

- Evaluating a new language or framework
- Reasoning about performance, safety, or correctness
- Comparing paradigms or execution models
- Diagnosing runtime or memory behaviour

**When Not to Use**

- Tool‑specific behaviour (Workbench)
- Operational instructions (Runbook)
- Project‑specific implementation details

---

## 🎯 What Problem Does This Solve?

Programming languages solve the problem of **expressing computation** in a structured, unambiguous, machine‑interpretable way.

They provide:

- **syntax** for expressing logic
- **semantics** that define meaning
- **paradigms** that shape how problems are modelled
- **type systems** that constrain or validate behaviour
- **execution models** that determine performance and safety
- **memory models** that define how data is stored and accessed
- **computational power** (Turing completeness)

A Technical Analyst must understand these forces to reason about architecture, performance, correctness, and system behaviour.

---

## 🧠 Conceptual Model

### Core Components

- **Syntax** — the grammar and structure of the language
- **Semantics** — the meaning of syntactic constructs
- **Paradigms** — the mental models the language supports
- **Type System** — how values are classified and validated
- **Execution Model** — compilation, interpretation, JIT, VM
- **Runtime Environment** — the system executing the code
- **Memory Model** — how memory is allocated, shared, and reclaimed
- **Turing Completeness** — whether the language can express all computations a Turing machine can perform

### Axes of Variation

- Static vs dynamic typing
- Strong vs weak typing
- Compiled vs interpreted
- Managed vs unmanaged memory
- Functional vs imperative vs OO vs logic paradigms
- Single‑threaded vs multi‑threaded runtimes
- Turing complete vs non‑Turing complete languages

---

### Typical Lifecycle or Flow

```
Human Intent
     ↓
Language Syntax (source code)
     ↓
Parsing → AST (Abstract Syntax Tree)
     ↓
Semantic Analysis (types, scope, correctness)
     ↓
Execution Model:
   - Compilation → Machine Code
   - Interpretation → Runtime Execution
   - JIT → Hybrid
     ↓
Runtime Environment
     ↓
Memory Model (stack, heap, GC)
     ↓
Program Behaviour
```

---

## "Frameworks & Libraries"


A **framework**, **library**, and **code** represent three layers of abstraction in software development.
They differ in **control**, **responsibility**, and **how much structure they impose**.

This page explains:

- what each layer *is*
- why each layer exists
- how they relate
- how to choose between them
- how they shape system behaviour

---

## 🧠 Theory

Frameworks, libraries, and code form a **hierarchy of abstraction**:

### **Framework → Library → Code**

- A **framework** provides structure, conventions, and inversion of control.
- A **library** provides reusable functions you call when needed.
- **Code** is your application logic — the part you own.

Frameworks solve **common problems** by providing pre‑built solutions.
Libraries solve **specific problems** by providing reusable components.
Code solves **your domain problem**.

---

:::tip
### Definition
A **framework** is a pre‑packaged set of solutions that solves common development problems through **inversion of control**.
:::

**When to Use**

- When the problem domain is well‑understood (web apps, APIs, security, UI)
- When you want conventions, structure, and guardrails
- When you need rapid development with predictable patterns

**When Not to Use**

- Highly bespoke systems
- Low‑level performance‑critical code
- Domains where the framework’s constraints become limiting

---

## 🎯 What Problem Does This Solve?

Frameworks and libraries exist to solve **recurring engineering problems**:

- routing
- templating
- authentication
- state management
- dependency injection
- concurrency
- persistence
- testing
- configuration

Without them, every team would rebuild the same infrastructure repeatedly.

Frameworks provide **structure**.
Libraries provide **capability**.
Code provides **business value**.

---

## 🧠 Conceptual Model

### **Core Components**

- **Framework** — owns the flow; you fill in the gaps
- **Library** — you call it when needed
- **Code** — your domain logic
- **Inversion of Control** — framework calls *your* code
- **Dependency Injection** — externalising object creation
- **Convention over Configuration** — predictable defaults

### **Axes of Variation**

- Opinionated ↔ Unopinionated
- Heavyweight ↔ Lightweight
- Declarative ↔ Imperative
- Convention‑driven ↔ Configuration‑driven
- Full‑stack ↔ Single‑purpose

---

### Typical Lifecycle or Flow

```
[Framework Bootstraps App]
          ↓
[Framework Handles Routing / Events]
          ↓
[Framework Calls Your Code]
          ↓
[Your Code Calls Libraries]
          ↓
[Libraries Perform Specific Tasks]
```

---

| Performance bottlenecks | Middleware, ORMs, DI containers |


## "Data Structures"


:::tip
### Definition
Data Structures & Conditionals describe how software organises information and makes decisions, forming the foundation of performance, correctness, and system behaviour.
:::

**When to Use**

- Understanding performance characteristics
- Evaluating system behaviour under load
- Reviewing logic, branching, or data access patterns
- Debugging slow or incorrect behaviour
- Designing flows, pipelines, or decision rules

**When Not to Use**

- When discussing storage systems (use Storage Theory instead)
- When modelling domain entities (use Data Modelling)
- When evaluating distributed behaviour (use Communication Patterns)
- When logic belongs in state machines or workflow engines

---

## 🎯 What Problem Does This Solve?

Data Structures & Conditionals solve the problem of **how systems organise information and choose actions**.
They give Technical Analysts the mental models needed to:

- Predict performance and scaling behaviour
- Understand why systems slow down or misbehave
- Evaluate branching logic for correctness
- Identify bottlenecks caused by repeated scans or poor structure
- Communicate clearly with engineers using shared vocabulary

---

## 🧠 Conceptual Model

Software behaviour emerges from two primitives:

### Core Components

#### **1. Data Structures**
How data is *organised* and *accessed*.

#### **2. Conditionals**
How decisions are *made* based on that data.

Together, they determine:

- What the system *knows*
- How it *chooses*
- How it *scales*
- How it *responds* under load

### Axes of Variation

- **Ordered vs Unordered** (lists vs sets)
- **Indexed vs Keyed** (arrays vs maps)
- **Linear vs Hierarchical** (lists vs trees)
- **Deterministic vs Branching** (simple vs nested conditionals)
- **Constant‑time vs Linear‑time** (O(1) vs O(n))

---

### Typical Lifecycle or Flow

```mermaid
flowchart TD
    A[Input Data] --> B[Choose Data Structure]
    B --> C[Apply Conditional Logic]
    C --> D[Perform Operation (lookup/insert/traverse)]
    D --> E[Return Result or Trigger Action]
    E --> F[Performance Changes as Data Grows]
```

## 🔍 TA Lens

:::info How a TA Evaluates This Concept
- Identify the **problem shape** and map it to the right structure
- Look for repeated linear scans (O(n))
- Evaluate branching logic for clarity and completeness
- Understand how structure and logic behave under load
- Surface risks around ordering, uniqueness, or lookup speed
:::

**What happens when:**

- **Data grows** → linear scans become bottlenecks
- **Traffic increases** → branching logic becomes hot paths
- **Concurrency rises** → shared structures become contention points
- **Resources become constrained** → inefficient structures degrade sharply

## 🧬 Variants / Types

<Tabs>

<TabItem value="collections" label="Collections">

### Collections

#### Arrays / Lists

```
Index → 0  1  2  3
        [A][B][C][D]
```

**Purpose**
Ordered, index‑based storage.

**Key Characteristics**
- Fast indexed access
- Good for scans
- Slow inserts/deletes

**Behaviour**
Performance degrades linearly as size grows.

**Trade-offs**
Simple and predictable, but costly for mutation.

---

#### Sets

```
{ A, B, C }   // No duplicates
```

**Purpose**
Uniqueness and fast membership checks.

**Key Characteristics**
- O(1) lookup
- No ordering

**Behaviour**
Ideal for deduplication and “contains?” checks.

**Trade-offs**
Hashing overhead; no positional access.

---

#### Maps / Dictionaries

```
Key → Value
A   → 1
B   → 2
```

**Purpose**
Fast lookup by key.

**Key Characteristics**
- O(1) access
- Natural modelling of relationships

**Behaviour**
Excellent for caching, indexing, and routing.

**Trade-offs**
Memory overhead; collisions degrade performance.

---

#### Queues (FIFO)

```
Front → [A][B][C] → Back
```

**Purpose**
Ordered processing.

**Use When**
Task scheduling, message processing.

---

#### Stacks (LIFO)

```
Top → [C]
       [B]
       [A]
```

**Purpose**
Last‑in, first‑out behaviour.

**Use When**
Undo operations, DFS traversal.

</TabItem>

<TabItem value="trees" label="Trees & Graphs">

### Trees

```
      A
     / \
    B   C
```

**Purpose**
Hierarchical modelling.

**Key Characteristics**
- Fast search when balanced
- Depth affects lookup

**Behaviour**
Used in indexing, routing, and file systems.

**Trade-offs**
Unbalanced trees degrade to linear behaviour.

---

### Graphs

```
A — B — C
 \     /
   D
```

**Purpose**
Model relationships and networks.

**Key Characteristics**
- Flexible structure
- Supports cycles

**Behaviour**
Used in routing, dependencies, social graphs.

**Trade-offs**
Traversal cost varies; cycles complicate logic.

</TabItem>

<TabItem value="bigo" label="Big‑O Intuition">

### Big‑O (TA Edition)

You don’t need formulas — you need **shapes**.

| Operation | Array/List | Set | Map |
|-----------|------------|-----|-----|
| Lookup | O(n) | O(1) | O(1) |
| Insert | O(n) | O(1) | O(1) |
| Delete | O(n) | O(1) | O(1) |

:::note TA Takeaway
Repeated linear scans (O(n)) are the root cause of many performance issues.
:::

</TabItem>

<TabItem value="conditionals" label="Conditionals & Control Flow">

### Conditionals

#### IF / ELSE — Binary Decisions

**Purpose**
Choose between two behaviours.

**Key Characteristics**
- Simple branching
- Clear fallback path

**Behaviour**
```
WHEN <condition>
THEN <action>
ELSE <fallback>
```

---

#### Multi‑branch (IF / ELIF / ELSE)

**Purpose**
Choose between multiple paths.

**Behaviour**
```
WHEN <A> → <action A>
WHEN <B> → <action B>
ELSE → <fallback>
```

---

#### CASE / SWITCH — Category Decisions

**Purpose**
Match categories or types.

**Behaviour**
```
WHEN <category1> → <action1>
WHEN <category2> → <action2>
OTHERWISE → <fallback>
```

---

#### Loops — Repeated Conditional Behaviour

**FOR** → known iteration count
**WHILE** → repeat while condition is true
**UNTIL** → repeat until condition becomes true

---

#### Functions — Encapsulated Logic

**Purpose**
Group conditional logic into reusable units.

**Behaviour**
```
DEFINE function:
    WHEN <condition>
    THEN <action>
    ELSE <fallback>
```

## 💥 Outputs / Results

:::note Special Considerations
Performance issues often arise from structure/logic mismatches rather than code bugs.

### Success Modes

| Result Type | Description |
|-------------|-------------|
| Predictable Performance | Operations scale as expected |
| Clear Decision Logic | Branching is explicit and correct |
| Efficient Access Patterns | Minimal scanning or unnecessary work |
| Stable Behaviour Under Load | No sudden degradation |

### Failure Modes

| Failure Type | Description |
|--------------|-------------|
| Linear Scan Bottlenecks | Repeated O(n) operations |
| Incorrect Branching | Missing or contradictory conditions |
| Explosive Traversal | Graph cycles or deep recursion |
| Unnecessary Sorting | Wasted computation in pipelines |

# 📘 Git Version Control

:::tip

## Git Version Control

**What is it?** 
Git is a distributed version control system used to track changes in source code, collaborate across engineering teams, manage branching models, and coordinate reproducible code releases.

### 📚 Related Theory References
* Workflows & Orchestration — Core branching models, release governance, and version control architecture.
:::

## 🧭 When to Use It

| When to Use | When Not to Use |
| :--- | :--- |
| • Tracking source code history and collaborative multi-developer development.<br>• Managing feature branches, pull requests, and code reviews.<br>• Release management, tagging, and CI/CD pipeline event triggers. | • Storing large binary artifacts (use specialized artifact storage or LFS instead).<br>• Real-time collaborative document editing.<br>• Managing massive datasets (use specialized tools like DVC or LakeFS). |

## 🚀 Getting Started & Prerequisites

What prerequisites, dependencies, or initial configurations are required before interacting with Git?
1. **Local Environment:** Git CLI installed locally (`git --version`) alongside an active SSH client or credential helper.
2. **Configuration Setup:** Global user identity settings (`git config --global user.name` and `git config --global user.email`) and registered SSH keys or authentication tokens.

---

## 🔑 Tool Requirements

* **Access URL / Portal:** Hosted repository portal (e.g., GitHub, GitLab, or Bitbucket enterprise URL).
* **Authentication Method:** SSH keys (`id_rsa` / `id_ed25519`) or personal access tokens (PATs) with repository write permissions.
* **Initial Setup Check:** Verify remote access connectivity and authentication state using command-line probes (`git ls-remote <repo_url>`).

## 📋 Common & Useful Workflows

```bash
# 1. Initialize local configuration and set identity
git config --global user.name "Engineering User"
git config --global user.email "engineer@enterprise.com"

# 2. Create and switch to a new feature branch
git checkout -b feature/my-new-feature

# 3. Stage changes, commit with a descriptive message, and push to remote
git add .
git commit -m "feat: implement core feature logic"
git push origin feature/my-new-feature

# 4. Sync local repository with main and rebase changes
git fetch origin
git checkout main
git pull origin main

# 5. Tag a production release and push tags
git tag -a v1.0.0 -m "Release version 1.0.0"
git push origin v1.0.0

```

## 🚨 Operational Triage Snapshots

:::danger
Quick-reference diagnostics for common Git version control failures:
:::

| Symptom / Telemetry | Root Cause | What to Check | Immediate Action |
| --- | --- | --- | --- |
| **Cannot Clone Repository** | Incorrect repository URL, network connectivity issue, or missing SSH credentials. | Remote repository URL, network routes, and local SSH key configuration. | Correct URL spelling, verify VPN/network access, and check SSH agent keys. |
| **Merge Conflicts** | Concurrent modifications to the same file lines across branches. | `git status` and file diff markers (`<<<<<<<`, `=======`, `>>>>>>>`). | Edit conflicted files manually to resolve lines, stage resolved files, and complete the merge. |
| **Push Rejected** | Remote branch contains commits not present locally, or branch protection rules block force pushes. | Branch protection policies and `git log` divergence state. | Pull latest changes (`git pull --rebase`), resolve conflicts, and re-attempt push. |
| **Detached HEAD State** | Explicitly checked out a specific commit hash rather than a branch pointer. | `git status` output indicating HEAD position. | Create a temporary branch to preserve work (`git checkout -b temp-branch`) or switch back to the target branch. |

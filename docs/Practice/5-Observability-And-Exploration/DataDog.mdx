# 📘 Datadog Observability Platform

:::tip

## Datadog Observability Platform

**What is it?** 
Datadog is a cloud-based observability and security platform that unifies logs, metrics, distributed traces, dashboards, and alerting. It provides end-to-end visibility into distributed microservices and cloud infrastructure.

### 📚 Related Theory References
* Observability & Exploration — Architecture of unified telemetry, metric collection, and distributed tracing contracts.
:::

## 🧭 When to Use It

| When to Use | When Not to Use |
| :--- | :--- |
| • Unified production log, metric, and trace correlation across microservices. • Setting up cross-service APM service maps and real-time alerts. • Fast operational root-cause analysis during incident triage. | • Environments requiring zero data export to third-party SaaS due to strict compliance. • Simple, static systems where native cloud metrics (e.g., basic CloudWatch) suffice. • Extremely low-budget logging footprints where SaaS ingestion costs outweigh benefits. |

## 🚀 Getting Started & Prerequisites

What prerequisites, dependencies, or initial configurations are required before interacting with Datadog?
1. **Local Environment:** Datadog agent installed on compute hosts or Kubernetes clusters, with cURL and CLI tools available.
2. **Configuration Setup:** API keys (`DD_API_KEY`), Application keys (`DD_APP_KEY`), and appropriate site endpoints configured (`datadoghq.eu` or `datadoghq.com`).

---

## 🔑 Tool Requirements

* **Access URL / Portal:** Datadog enterprise tenant web portal (e.g., `https://app.datadoghq.eu`).
* **Authentication Method:** Datadog API/App keys or corporate Single Sign-On (SSO / SAML).
* **Initial Setup Check:** Verify agent connectivity and health indicators using agent status commands or the Datadog infrastructure dashboard before deploying new instrumented workloads.

## 📋 Common & Useful Workflows

```bash
# 1. Export authentication credentials and install/verify the Datadog agent
export DD_API_KEY="your-api-key"
export DD_APP_KEY="your-app-key"
sudo datadog-agent status

# 2. Restart the Datadog agent service to apply configuration changes
sudo systemctl restart datadog-agent

# 3. Send a custom metric via the Datadog HTTP API
curl -X POST \
  -H "DD-API-KEY: $DD_API_KEY" \
  -H "DD-APP-KEY: $DD_APP_KEY" \
  -H "Content-Type: application/json" \
  -d '{"series":[{"metric":"custom.metric","points":[[1710000000, 42]]}]}' \
  "[https://api.datadoghq.eu/api/v1/series](https://api.datadoghq.eu/api/v1/series)"

# 4. Tail agent logs or generate a diagnostic flare bundle
sudo datadog-agent flare

```

## 🚨 Operational Triage Snapshots

:::danger
Quick-reference diagnostics for common Datadog platform and telemetry failures:
:::

| Symptom / Telemetry | Root Cause | What to Check | Immediate Action |
| --- | --- | --- | --- |
| **Missing Logs** | Agent misconfigured, log collection disabled, or pipeline rules dropping data. | `datadog-agent status`, tail logs, and Log Pipeline JSON rules. | Fix log collection paths in `datadog.yaml`, restart the agent, or update pipeline filters. |
| **Missing Metrics / APM Traces** | SDK instrumentation missing, API key invalid, or network egress blocked. | Environment variables (`DD_API_KEY`, `DD_SITE`), firewall rules, and app startup logs. | Validate API key permissions, open outbound port 443, and ensure APM libraries are initialized. |
| **Alert Noise / False Positives** | Overly sensitive monitor thresholds or missing multi-signal context. | Monitor evaluation queries, historical trigger frequency, and alert grouping tags. | Tune threshold boundaries, add anomaly detection, or group alerts by environment/service. |
| **High Cardinality Spikes** | Unbounded tag generation (e.g., user IDs or unique request UUIDs as tags). | Metric tag counts, dashboard query performance, and indexing metrics. | Strip high-cardinality tags from instrumentation code and aggregate metrics upstream. |

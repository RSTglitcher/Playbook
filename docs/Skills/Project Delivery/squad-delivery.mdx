# 📘 Squad Delivery & Technical Execution

:::tip

## Squad Delivery & Technical Execution

**What is it?** 
A structured delivery and facilitation skill used within cross-functional engineering squads to drive feature flow, manage Work-In-Progress (WIP) limits, clear technical blockers, and maintain delivery momentum from sprint planning through deployment.

#### 📚 Related Theory & Practice References
* Theory — Agile delivery governance, value stream mapping, and continuous delivery principles.
* Practice — Jira backlog tracking, team sprint workflows, and technical ticketing standards.
:::

## 🧭 When is it Used?

| When to Use | When Not to Use |
| :--- | :--- |
| • Ongoing daily execution within an embedded product engineering squad and sprint planning cycles. • Managing feature rollouts, tracking sprint burndown telemetry, and resolving cross-squad blockers. • Coordinating release verification and ensuring adherence to the Definition of Done (DoD). | • Handling emergency production incidents requiring dedicated incident response playbooks. • Performing isolated solo code debugging or writing unit implementation tests. |

---

## 💡 What Value Does It Bring?

* **Ensures Predictable Velocity:** Replaces chaotic task switching with structured feature flow, ensuring sprint commitments are met consistently.
* **Eliminates Delivery Blockers:** Proactively uncovers and clears non-engineering friction (e.g., missing API contracts or design assets) before they stall development.
* **Aligns Product & Engineering:** Bridges business priorities with engineering execution through clear Definition of Ready (DoR) and Definition of Done (DoD) gates.

---

## 🧠 Core Concepts

| Concept / Mechanism | Plain English Explanation | Execution Impact |
| :--- | :--- | :--- |
| **Work-In-Progress (WIP) Limits** | Restricting the number of active tasks a developer or squad can handle simultaneously. | Forces completion of existing work before starting new tasks, drastically reducing context switching and code review bottlenecks. |
| **Definition of Ready (DoR) Gate** | The strict checklist criteria a user story must satisfy before it can be pulled into an active sprint. | Prevents half-baked or ambiguous requirements from entering development and causing mid-sprint churn. |
| **Flow-Centric Standups** | Daily coordination focused on unblocking work items rather than status reporting. | Keeps engineers focused on moving tickets across the board toward completion rather than listing personal updates. |

---

## 📋 Common Patterns

1. **Phase 1: Sprint Planning & DoR Verification** — Collaborate with Product Owners and Engineering Leads to set velocity-based goals and verify incoming tickets meet DoR criteria.
2. **Phase 2: Daily Flow & Blocker Management** — Facilitate daily standups to monitor WIP, clear technical or dependency blockers, and track PR turnaround times.
3. **Phase 3: Mid-Sprint Tracking & Release Sign-Off** — Manage scope trade-offs for unplanned work, verify staging acceptance criteria, and ensure adherence to the Definition of Done (DoD).

## 🛠️ Practical Tips & Templates

> **Template / Artifact Example:** Squad Sprint Execution & Delivery Checklist.

```markdown
# Squad Delivery Checklist

## Pre-Sprint / Planning
- [ ] Sprint goals clearly articulated and linked to top backlog epics.
- [ ] All sprint tickets estimated and meet Definition of Ready (DoR).
- [ ] Team capacity accounts for planned PTO, on-call duties, and support work.

## In-Sprint Execution
- [ ] Daily standup focused on unblocking WIP rather than status reporting.
- [ ] PR turnaround times monitored (<24h target).
- [ ] Mid-sprint scope changes explicitly negotiated and logged.

## Release & Post-Sprint
- [ ] Acceptance criteria validated in staging environment.
- [ ] Release notes published to stakeholder channels.
- [ ] Sprint retro items logged for continuous improvement.

```

:::warning

### Pitfalls & Edge Cases

* **Common Mistake:** Allowing scope creep mid-sprint without dropping lower-priority items, leading to missed sprint goals and team burnout.
* **Pro Tip:** Focus on completing tickets sequentially rather than starting multiple items simultaneously. Pushing a single ticket to "Done" provides far more value than five tickets sitting at 80% complete.
:::

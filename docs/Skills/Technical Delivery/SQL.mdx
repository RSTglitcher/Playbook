# 📘 SQL & Relational Database Queries

:::tip

## SQL & Relational Database Queries

**What is it?** 
A structured technical skill used to interact with relational databases, defining schema structures, manipulating records, and executing declarative queries to extract and transform structured data.

#### 📚 Related Theory & Practice References
* Theory — Relational database modeling, set theory, and ACID transaction guarantees.
* Practice — Database client tooling, analytical warehouses, and schema migration runners.
:::

## 🧭 When is it Used?

| When to Use | When Not to Use |
| :--- | :--- |
| • Querying analytical data warehouses (e.g., BigQuery, Snowflake) or relational databases (PostgreSQL, MySQL). • Designing tables, defining foreign key constraints, and writing database schema migrations. • Performing data exploration, aggregation, and joining across multiple relational datasets. | • Managing unstructured document stores or binary blob storage where relational joins do not apply. • Writing application business logic or complex UI-rendering components. |

---

## 💡 What Value Does It Bring?

* **Enforces Data Integrity:** Relational constraints and schemas guarantee consistent, valid, and structured data storage.
* **Declarative Power:** Allows engineers and analysts to specify *what* data to retrieve rather than writing procedural looping logic.
* **Scalable Analytics:** Handles millions of rows efficiently through database engine optimization and columnar storage.

---

## 🧠 Core Concepts

| Concept / Mechanism | Plain English Explanation | Execution Impact |
| :--- | :--- | :--- |
| **Set-Based Execution** | Treating query results as mathematical sets rather than procedural, row-by-row operations. | Enables database engines to optimize query execution paths dynamically. |
| **Relational Joins** | Combining rows from two or more tables based on related column values (e.g., foreign keys). | Reconstructs fragmented domain data into cohesive analytical views. |
| **Aggregation & Grouping** | Grouping rows sharing common attributes to compute summary metrics (COUNT, SUM, AVG). | Transforms raw transactional rows into meaningful business intelligence metrics. |

---

## 📋 Common Patterns

1. **Phase 1: Schema Definition & DDL** — Create tables, define primary/foreign keys, and configure appropriate data types.
2. **Phase 2: Data Manipulation & Ingestion** — Insert, update, or delete records using transactional DML statements.
3. **Phase 3: Querying & Analytical Exploration** — Extract insights using filters, multi-table joins, aggregations, and subqueries.

## 🛠️ Practical Tips & Templates

> **Template / Artifact Example:** SQL Fundamentals and Query Patterns.

```sql
-- 1. Basic Data Definition (DDL) & Types
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
    is_active BOOLEAN DEFAULT TRUE,
    created_date DATE DEFAULT CURRENT_DATE
);

-- 2. Basic Data Insertion (DML)
INSERT INTO products (product_id, name, price) 
VALUES (1, 'Notebook', 4.99);

-- 3. Basic Query & Filtering (Hello World equivalent)
SELECT product_id, name, price 
FROM products 
WHERE is_active = TRUE 
ORDER BY price DESC 
LIMIT 5;

-- 4. Relational Joins & Aggregations
SELECT 
    c.name AS customer_name,
    COUNT(o.order_id) AS total_orders,
    SUM(o.total_amount) AS lifetime_spend
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name
HAVING SUM(o.total_amount) > 500
ORDER BY lifetime_spend DESC;

```

:::warning

### Pitfalls & Edge Cases

* **Common Mistake:** Forgetting to include grouped columns in the `GROUP BY` clause, or misusing `WHERE` instead of `HAVING` when filtering aggregated results.
* **Pro Tip:** Always define explicit foreign key indexes and avoid using `SELECT *` in production code to minimize unnecessary network and memory overhead.
:::

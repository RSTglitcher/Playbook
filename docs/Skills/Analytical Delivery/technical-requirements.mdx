# 📘 Requirements

:::tip

## Technical Requirements & Specification

**What is it?** 
A structured engineering skill focused on eliciting, formalizing, and documenting functional and non-functional requirements to establish unambiguous engineering specifications before design or coding begins.

### 📚 Related Theory & Practice References
* Theory — System architecture governance, scalability planning, and non-functional constraint modeling.
* Practice — Architecture documentation, system mapping, and technical refinement workflows.
:::

## 🧭 When is it Used?

| When to Use | When Not to Use |
| :--- | :--- |
| • Initiating greenfield projects, major feature epics, or complex cross-service integrations. • Establishing clear service-level agreements (SLAs), throughput targets, and security constraints. • Resolving ambiguous product requests into concrete, testable engineering specifications. | • Fixing trivial bug reports or making isolated code tweaks within an existing bounded context. • Routine sprint task grooming where user stories are already fully specified. |

---

## 💡 What Value Does It Bring? (Problem Solved)

* **Eliminates Misalignment:** Prevents costly mid-development pivots by securing explicit agreement on system constraints early.
* **Sets Performance Boundaries:** Explicitly defines scalability, latency, availability, and security expectations upfront.
* **Streamlines Auditing:** Provides a definitive technical baseline for code reviews, architectural decisions, and QA test plan generation.

---

## 🧠 Core Concepts

| Concept / Mechanism | Plain English Explanation | Execution Impact |
| :--- | :--- | :--- |
| **Functional vs. Non-Functional Requirements** | Functional requirements dictate *what* the system does (business logic); non-functional dictate *how well* it does it (performance, security, scalability). | Ensures teams don't just build features that work, but features that scale reliably under production load. |
| **Constraint Boundary Mapping** | Documenting hard limits imposed by infrastructure, compliance, or external API contracts. | Prevents architectural designs that violate regulatory standards or hardware limits. |
| **Acceptance Thresholds** | Measurable quantitative targets (e.g., p99 latency < 200ms, 99.99% uptime). | Replaces vague performance goals with strict, testable engineering metrics. |

---

## 📋 Common Patterns

1. **Phase 1: Stakeholder Discovery & Constraint Extraction** — Interview product managers, security engineers, and platform teams to gather performance, security, and functional constraints.
2. **Phase 2: Specification Document Drafting** — Formalize gathered criteria into structured technical requirements documents (TRDs) covering data models, APIs, and SLAs.
3. **Phase 3: Technical Review & Sign-Off** — Walk through the requirements specification with engineering and architecture leads to validate feasibility before sprint execution.

## 🛠️ Practical Tips & Templates

> **Template / Artifact Example:** Technical Requirements Document (TRD) Confluence Structure.

```markdown
# Technical Requirements Document: [Project Name]

## 1. Overview & Objectives
- **Problem Statement:** [What problem are we solving?]
- **Proposed Solution:** [High-level technical approach]

## 2. Functional Requirements
- FR-01: System shall allow authenticated users to export transaction reports in CSV format.
- FR-02: System shall trigger webhook notifications upon successful payment settlement.

## 3. Non-Functional Requirements (NFRs)
- **Performance:** API response times must maintain a p99 latency of < 250ms under peak load.
- **Scalability:** Must support horizontal scaling up to 10,000 concurrent websocket connections.
- **Security:** All data at rest must be encrypted using AES-256; transit secured via TLS 1.3.

## 4. Dependencies & Constraints
- Upstream payment gateway API rate limit of 50 requests/second.
- Requires AWS RDS PostgreSQL multi-AZ migration.

```

:::warning

### Pitfalls & Edge Cases

* **Common Mistake:** Omitting non-functional constraints (like latency or security limits) until after code is written, leading to costly rewrites.
* **Pro Tip:** Always tie every technical requirement back to a measurable validation test so QA can verify compliance automatically in CI/CD pipelines.
:::
